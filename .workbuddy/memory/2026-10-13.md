## 澄清：agent 的产出不是 patch 文件，而是直接改源文件（问答）

- 用户问「模型产出的是 patch 文件，还是直接动了仓库里的源文件」→ 答案：**直接改源文件**，磁盘上不存在 patch 产物。
- 机制链：agent 进程 cwd = `sb.Root()`（`runner.newSandbox` → `sandbox.NewLocal`，agent 经 `sb.ExecStream` 运行）；
  模型输出的是 Edit/Write 的 tool call，源文件就地被改；run 结束后 `runner.changedSet` → `Baseline.Diff`
  （`workspace.go` 先 `git add -A -N` 让 untracked 进 diff，再 `git diff <baseline SHA>`）**反算**出补丁，
  落进 `att.Diff`；`grader/patch.go` 消费的就是这串 diff 字符串，不读任何文件。
- `output.type`（`dataset/spec.go:92-101`）是**期望契约**（决定 grader 看什么），**不是产出格式**：
  `patch` = 期望工作树有改动 / `files` / `stdout`（给 exact_match、llm_judge）/ `none`。
- 推论：agent 自行 `git commit` 不影响 diff（baseline SHA 固定，`git diff <SHA>` 仍成立）；
  但 `git checkout`/`reset --hard` 会把改动抹掉，后态里看不出来。
- 对「环境固化」方案的含义：没有独立 patch 可摘 → 会话结束时的目录状态 = 初始环境 + 答案，**二者不可分离**；
  所以采集到的快照必然是**后态**，`dirty` 层（已修改+未跟踪）语义上就是答案本身 —— git 场景默认不带是对的。

## collect 该不该收 dirty（问答）

- **dirty 要分两类**：会话开始前就存在的未提交改动 = **环境**（该收）；会话自己造成的改动 = **答案**（绝不能收）。
- **collect 分不开这两类**：转录只记分支（`s.GitBranch`）不记 commit，也没有文件系统历史；采集时刻手上只有一个后态工作树。
  而且前者可能已被后者覆盖 → 会话开始时的状态不可恢复。所以在"分不开"的前提下，**宁可少收**（少收=起点偏差，可披露；多收=静默塞答案）。
- **`EditedFiles` 不完整，不能当剥离依据**：它来自转录的 `file-history-snapshot` 记录里的 `Snapshot.TrackedFileBackups`
  （`parse.go:428-432`、`cursor.go:726`），即 **Edit/Write 工具碰过的被跟踪文件**；
  Bash 写入（`echo > f`、脚本产物、`git apply`）不在其中。且它是**累计集合**不是逐轮 delta（`editedFiles` 注释已说明）。
- **现状**：`bindCwd`（`collect.go:395-427`）只写 `{type:git, repo:cwd, ref:分支名}`，什么都不拷，理由写在函数注释里
  （"copying the directory as it stands now would hand the replay a tree that already contains whatever that session did"）；
  非 git / 无提交的目录**直接报错**（同一条理由）。**缺口：它不检测 dirty，读者不知道丢了一块起点。**
- 建议：P0 = `bindCwd` 跑一次 `git status --porcelain`，把未提交改动的文件数写进 note（**报告**，不是收集）；
  P1 = `--snapshot-pre-session` 用 `EditedFiles` 做 best-effort 反向剥离，剥不掉的部分必须声明。
- 另一处漂移源：`ref` 是**分支名**，会移动 → 回放起点其实还没被钉住（要靠上轮的 `workspace.type: snapshot` 内容寻址解）。

## 不收会话改动，回放时怎么比较（问答）

- **比较的对象不是文件，是账本。** `store.BaselineComparison`（`store.go:263-296`）只有：
  `Tokens` / `Ms`(busy) / `Cost` / `Turns` / `Output`(录制方最后一条非空 assistant 文本) /
  `AgentName` / `AgentModel` / `Source` / `Notes` —— **没有任何文件、diff 或答案目录**。
- 三层比较：① 代价（`TokenDelta`/`MsDelta`，`store.go:331-355`）；② 结论（`Output`，注释原文 "kept so the report
  can set the two conclusions side by side"）；③ 对错（grader 的事，与 baseline 无关）。
- 准入规则在 `Attempt.ComparableBaseline()`（`store.go:316-321`）：`Baseline.Present` 为假或本 cell `CellError` 则**不可比**；
  timeout 可计入（真的花了预算）。delta 的分母为 0 时返回 `ok=false`，**不做减法**（"零是没测到，不是测到零"）。
- **答案没被丢**：它以两种形式早就在数据集里 —— `Baseline.FinalOutput`（结论）与
  `Baseline.Turns[].Tools[].Input`（Edit/Write 的 tool call 参数里带着路径 + **新内容本体**）。
  「工作区里没有答案」≠「数据集里没有答案」：前者是**回放起点**，后者是**参照系**。
- **会话改动是终点，不是起点** —— 会话开始时它还不存在，所以不收它**不损失可比性**，反而收了才会把起点变成终点。
  与上一条的"会话前 dirty"性质相反：那个不收才是**起点偏早、可比性有损**（要报告）。
  两条"不收"意义不同，别混为一谈。
- 若将来要比"改动"（新 agent 的 `att.Diff` vs 录制方补丁）：原料是**转录里的 tool call**（重放出来），不是 dirty。

## 采集若跑在 docker sandbox 里，回放会更简单吗（问答 / 设计）

- **先纠正一个前提：今天的 docker 后端不是"环境在容器里"，而是"执行在容器、环境在宿主"。**
  `sandbox.DockerConfig.Root`（`docker.go:18-19`）注释原文 "the host directory bind-mounted into the container"；
  `Image`（`docker.go:20-22`）只负责"含 agent CLI 和依赖"。`start()` 即 `docker run -v host:container ... image sleep infinity`。
  → 所以**沿用今天的模型，采集跑在容器里一点都不解决问题**：会话改的仍是宿主目录，`bindCwd` 的三条毛病（不记 commit /
  不分 dirty / ref 是分支名会漂移）原封不动。
- **有用的那种模型**：环境 = 镜像层，而不是 bind-mount。
  `docker run <image>` 那一刻就固定了起点；会话写入落在容器可写层。于是"会话前"= 镜像（digest 内容寻址）、
  "会话改动" = 可写层（`docker diff` 列得出）—— **两者物理分层**，上一轮那套 snapshot 设计里最复杂的三块
  （dirty 层、`EditedFiles` 反向剥离、三档可信度）**直接不需要**。
- **真正的简单性来源不是 docker，而是"起点在会话开始前就被固化"**。上一轮方案必须在**后态**上下刀（collect 是事后跑的），
  所以躲不开泄漏；容器模型下起点锚在 `docker run` 那一刻。同样的约束不用 docker 也能达到（规定会话前先 commit / 先打快照），
  但 docker 让它**结构性**成立而不是靠纪律。
- 回放侧省掉的：`Materialize` 四分支塌缩成"以镜像为根"；`ref` 漂移消失（digest 不动）；local / docker 两个后端收敛成同一动作。
- **不会自动变简单的**：① 转录里**没有**"会话是从 image X@digest 起的"这条锚点 —— 采集侧要新增"记录并证明起点"的职责；
  ② 只有会话跑在**新起的**容器里才干净，长期在跑的开发容器里可写层混着全部历史 → 又回到分不开；
  ③ volume / env / home 配置（`~/.claude/skills`、`.gitconfig`）在镜像之外；④ 平台绑定（amd64/arm64）与体积。
- 落点建议：`workspace.type: snapshot` 保留为**降级路径**（无容器锚点时），新增 `type: image`（或让 docker 后端直接以 image 为根）。
- 采集契约的转变：从"打包文件"变成"记录锚点 + 证明"。

## 业界如何设置 agent 回放环境（调研，2026-10 联网核实）

**结论：业界的答案几乎统一 —— 环境是"一个预构建容器镜像 + 一个固定 commit"，不是"文件清单 + setup 脚本"。回放 = 拉镜像 + 起容器 + checkout。**

- **SWE-bench**：每实例一个预构建镜像 `swebench/sweb.eval.x86_64.<instance_id>`，镜像内 repo 已在 `/testbed` @ base_commit、
  conda env `testbed` 装好依赖。**三级镜像 key 做分层缓存**：`base_image_key`（语言基础）→ `env_image_key`（按环境**哈希**，
  可缓存）→ `instance_image_key`（实例专属）—— 几千实例不必几千个完整镜像，这是"大规模"的关键。
  实例字段区分 **`environment_setup_commit`（装依赖用）与 `base_commit`（评测起点）** —— 环境构建与任务起点是两个提交。
  2024-06 全面容器化。patch 应用走**三级宽容度**：`git apply` → `git apply --reject` → `patch --fuzz=5 -p1`。
- **Terminal-Bench（Stanford × Laude）**：每任务一个目录 `task.yaml` + `Dockerfile`(+`docker-compose.yaml`) + `tests/` + `solution.sh`；
  镜像名 `terminal_bench_<task>`，工作目录 `/app`。**端状态验证**（"checks the end state of the environment, not the agent's
  transcript"）。随 2.0 发布 **Harbor harness**：多 provider（Docker / Modal / Daytona / E2B / Runloop），可并行数千容器；
  每任务跑 5 次报 95% CI。两道质检：**canary check**（防训练污染）与 **Dockerfile reference check**（确保镜像里不含测试或
  oracle solution —— 否则 agent 可直接读答案）。
- **SWE-bench-Live / REPOLAUNCH（微软）**：**环境由 agent 自动构建**（读 README/CI → 选基础镜像 → ReAct 迭代装依赖 → 固化成
  镜像）。**"Time Machine" 机制**：强制包管理器只能看见 bug report 之前发布的版本，防依赖漂移。1,319 任务 / 93 仓库。
  2026-08 起要求提交方提供 rollout trajectory 人工复核，确认**只给了 problem statement + docker image**，防作弊。
- **SWE-rebench**：标准化脚手架（所有模型同一最小 ReAct 框架 + 相同 prompt/超参，跑 5 次报 SEM + pass@5）——
  专治 **scaffold inflation**；并按模型训练 cutoff 标污染风险。
- **PawBench（阿里通义）**：每测试单元独立容器，保留**执行轨迹 + workspace 产物 + 环境快照**；量化出 **Harness 分差最高 6.4 分
  ≈ 一次重大模型版本升级**（与 agenteval "harness 是一等变量"同一立论）。

**真实教训（比结论更有用）**：
1. **tag 会漂移**：E2B 报告 SWE-bench `:latest` 镜像现在带的 setuptools/pytest 比老测试能忍的新（astropy 把 deprecation
   warning 当 error）→ **假失败**。教训：**钉 digest，不用 tag**（印证上一轮"内容寻址"结论）。
2. **文件系统顺序**：部分实例跑整个测试套件，顺序依赖 `scandir` 顺序 → 非 Docker 文件系统上产生 PASS_TO_PASS 假失败；
   他们专门分类为 `ordering_artifact`。教训：环境差异会产出"看起来像 agent 失败"的噪声，要能**分类**。
3. **镜像里的 HEAD ≠ base_commit**：SWE-bench 镜像在 base_commit 之上加了自己的一个 commit（改构建文件），所以
   **agent 必须 `git -C /testbed diff`（相对 HEAD），而不是 reset 到 base_commit** —— "环境 = 镜像层 + 一个基线提交"的活样本。
4. **联网不可协商**：`network_mode="none"`，否则 agent 会 `pip install` 去"修"导入错误，评测变成测连通性。
   规模化手段：镜像缓存摊薄冷启动（Modal 预装测试依赖并缓存）；轻量替代 bwrap/user namespaces（冷启动 340ms → 3.4ms）。

**对 agenteval 的映射（缺口）**：① 业界用镜像表达环境，我们 `workspace.type` 四分支 —— 上一轮的 `type: image` 正是业界默认；
② 业界起点是"commit + 预构建镜像"，我们 `bindCwd` 只记**分支名**（最弱一档）；③ 业界 `network_mode=none`，而我们的
`DockerConfig.Network` **无默认值（空 = 不传 = docker 默认 = 联网）** —— 真实缺口；④ 业界"每任务每容器"，
我们的 `--chain-sessions` 是例外，必须在报告里声明。

## 本地（无容器）如何构建 baseline 数据集（设计咨询）

**核心难题**：本地录制下起点锚点无处可寻 —— 转录只记 `s.GitBranch`（分支名，会移动）不记 commit，而 collect 是事后跑的，
任何现场快照都是**后态**（含答案）。所以本地唯一的解法是：**把起点变成你显式声明并负责的东西**。

**关键发现（原料已在，只差接线）**：`Session.StartedAt`（`parse.go:91`，由转录时间戳算出）→ 写进了 `Baseline.StartedAt`
（`collect.go:333`）。因此可以用

```
git log --before=<transcript StartedAt> -n1 --format=%H
```

**反推出会话开始前的那个 commit** —— 会话中途自己 commit 了也不影响（`--before` 取更早的那个）。这正好补掉「`ref` 是分支名
会漂移」这条，且**不需要用户改工作习惯**。边界：会话前工作树若已 dirty，得到的起点**不含那些改动**（起点偏早）→ 仍需报告 dirty。

**四步规程**：① `collect --list --cwd <repo>` 先看；② `collect --workspace-cwd --split session --out ...`；
③ 用上面的 `git log --before` 把 `workspace.ref` 钉成 SHA（今天要手工；改了 `tasks.jsonl` 会让 `dataset_hash` 变，这是对的）；
④ `git bundle create <id>.bundle <ref>` 存进数据集旁（防仓库被删 / 分支移动），再 `aeval validate`。

**选会话的四条准则**（数据质量，collect 本身不判）：起点可复现（git 仓库 + 会话前干净）；任务单一明确（不是闲聊/多任务混杂）；
确有改动（否则无可测差异）；prompt 自足（`--split session` 只取第一个 prompt，后续上下文不进数据集）。
**grader 不必写**：转录没有 ground truth（`Options.Grader` 注释已说明这是刻意的）；想要"改了没/改在范围内"可用 `patch` grader，
它不需要 ground truth。

**建议的 P0（未实现）**：`collect --record-start` —— 采集时对每个 git 会话目录跑 `git log --before=<StartedAt> -n1`
→ 写进 `workspace.ref`；顺手检测 dirty 写进 notes。原料齐备、成本很低，一次堵掉"起点漂移"+"静默丢起点"两个缺口。

## `--cwd` 的作用（问答：只选不绑）

- `collect --cwd <dir>` = **「这个工作目录录过哪些会话，全都要」**，是**挑选器**，**不绑工作区**。
  实现：`session.ProjectDir(root, cwd)` 把 cwd 按 Claude Code 的编码（分隔符 → `-`）映射成
  `~/.claude/projects/<encoded>` 再列 `.jsonl`（`SourcesForCwd`）；cursor 侧 `CursorChatsForCwd` 比
  `WorkspaceDir`（先 `filepath.Clean`）。该编码**有损**（名字带 `-` 的目录与嵌套路径无法区分）→ 只用来**找**
  候选，cwd/branch 事实一律从转录正文读回。cwd 先按**调用者目录**绝对化（`absFlagPath`）。
- **优先级 `--session` > `--cwd` > `--latest`**（`collectSources` 的 switch），**不是互斥报错**：同时给会静默
  按前者取。
- **坑：`--list` 时 `--cwd` 被静默忽略** —— `cmdCollectList(srcKind, cursorDB, root, ...)` 签名里根本没有
  cwd，`--list` 分支在 flag 解析后直接 return。所以 `collect --list --cwd X` 列的是**全部**会话，不是 X 的。
- 绑工作区是另一个 flag（`--workspace-cwd`），两者无关。

## 会话内交互式 collect（「让用户自己决定收不收」）设计判断

**结论：把「挑选」和「锚定」拆开 —— 挑选留在事后（反而更好），锚定必须是实时（唯一可锚的时刻）。**
所以「给 Claude Code 做一个 collect 命令让用户勾」只答对了一半，且答错的那一半（挑选）恰好是便宜的。

- **挑选（哪些会话进数据集）：事后比实时好。** ① 判据是**结果属性**（任务单一 / 确有改动 / prompt 自足），
  会话开始时看不出来；② 实时勾选把默认值从"全都留着、事后筛"翻成"忘了就永久丢"，且丢得无声无息；
  ③ 选择信号**完全可从转录复原**，没有信息论理由提前决定。
- **锚定（起点是什么）：只有会话开始时能拿。** 转录只记 `GitBranch`（会移动），collect 事后跑只剩后态
  → 起点不可重建（`git log --before=<StartedAt>` 只是近似，且会话前 dirty 就失效）。**这才是真痛点。**
- **正确形状**：`SessionStart` **hook 自动写锚点 sidecar**（session id / cwd / `rev-parse HEAD` /
  `status --porcelain` 计数 / 时间戳 / 有容器则 image digest）→ 事后 `collect --list` 把锚点与转录
  **join** 起来，**连起点质量一起显示**（clean / N dirty / 未记录）→ 人看过成果再决定。即
  **hook 管锚、清单管挑**，而且这也让上一轮建议的 `collect --record-start` 有了更好的实现
  （CLI 版只能从 `StartedAt` 近似，hook 是精确记录）。
- **命令仍有位置，但槽位不同**：转录**装不下**的东西才值得让用户敲 ——「这是好样本」的意图标签，
  以及**验证提示**（"失败的测试是 TestX"）。后者是 collect 唯一结构上无法凭空造的（没有 ground truth），
  由**人**给 oracle 不违反"不替转录造判决"。
- **第三个选项（往往最贴合真实需求）**：按**仓库**决定一次，而不是按会话 —— 仓库里放个
  `.aeval/collect.toml`（"这个仓库是我搞评测的"）。持久、不依赖记忆、符合心智。
- **若要做命令，四个约束**：① **per-source** —— collect 支持 claude + cursor，命令只覆盖 claude，
  sidecar 存储必须按 `source/session_id` 中立；② 锚点**缺失也要能建数据集**，标成"未记录"
  （同 schema 那句「空 = 没记录 ≠ 记录为空」）；③ 与 **clean room 不冲突** —— 回放侧 aeval 会抹掉用户的
  skills/hooks（`--bare` / `--disable-slash-commands`），而 hook 装在**录制侧**用户自己的 Claude Code，两回事；
  ④ 锚点必须连同"那一刻工作树是否干净"一起声明。

## 会话开始记录锚点再 collect（可行性：可行，但有防污染闸门）

**结论：可行。机制存在、字段匹配、落点已在 aeval 侧打通；但本机上这个 hook 已经在污染 aeval 自己的回放。**

**SessionStart hook 的输入字段**（官方文档核实，版本 2.1.x）：
`session_id` / `transcript_path` / `cwd` / `hook_event_name` / `source`（`startup|resume|clear|compact`）/ `model`，
可选 `agent_type`、`session_title`。**matcher 就是 source**，所以"只在 startup 写"可以纯靠配置表达。
另有 `CLAUDE_ENV_FILE`（仅 SessionStart / Setup / CwdChanged / FileChanged）可持久化 env 给后续 Bash。
文档原话：**"SessionStart runs on every session, so keep these hooks fast"**，且**`-p`（headless）也会触发**。
→ 所以它必须只读 git 元数据、绝不 clone；而且**回放（`-p`）同样命中**。

**坑 1（最重）：hook 在回放里也触发，且本机已经在发生。**
`DefaultIsolation()` = `{Bare:true, StrictMCPConfig:true, DisableSlashCommands:true}`（`agent/agent.go:46`），
`--bare` 明确 "skips hooks (including user settings hooks)"（`agent.go:30`）。但**用户选定 `bare=false`（为保 skills）**
→ 用户的 `~/.claude/settings.json` hooks 全部生效 → SessionStart hook 在每次 aeval 回放里都跑。
**证据**：`~/.git-ai/internal/transcripts-db` 的 `sessions` 表里 **12 行 `repo_work_dir` 指向 `.../aeval...`**
（2026-10-12 13:34–20:41），即 aeval 的回放工作区已被记进用户的个人 git-ai 库。
**修法只能由 aeval 做**：在子进程环境种标记（链路 `Spec.Env`/`EnvFromHost` → `Local.buildEnv`，`local.go:160`），
hook 见到 `exit 0`。hook 自己**看不出**这是回放。

**坑 2：非 git 目录要如实写 null + 原因**，不能静默空（与 `bindCwd` 的两个分支同形）。
**坑 3：`resume`/`clear`/`compact` 会重复触发** → 按 `session_id` 写一次（已存在就退出），锚点属于会话的**首次**启动。

**额外收获：git-ai 已经做了这件事的一半（身份那半）。**
- `~/.git-ai/internal/transcripts-db` 的 `sessions` 表：`session_id`(s_xxx) / **`external_session_id`（= Claude 的 UUID，正是 collect 的 join 键）**
  / `tool` / `repo_work_dir` / `first_seen_at` / `watermark_value`。
- 覆盖 **claude 484 / cursor 332 / codex 31 / opencode 18**（共 865，2026-06 起）—— 跨工具会话索引，
  collect 支持的两种来源都在。
- **但它不给锚点**：`~/.git-ai/internal/db` 的 `prompts` 表 7 行 `commit_sha` **全为 NULL**。
- **`first_seen_at` 不能当会话开始时间**：865 会话只有 **335 个不同时刻**，且 `2026-08-14 10:31:45` 一秒内 **207 条**
  （2026-06-17 13:53:3x 三秒内 224 条）→ 是**批量扫描**，不是逐会话触发。这条捷径要堵死。

**最小可行形状**：① aeval 种 `AEVAL_REPLAY`（防污染）；② hook 只在无标记且 `source=startup` 时写
`{session_id, cwd, head, dirty_count, not_a_repo?, ts}`；③ collect 按 `session_id` join sidecar；
④ 缺 sidecar → 标 `unrecorded`，不阻塞。
**更省的变体**：身份半边复用 git-ai 的 `external_session_id`，只让新 hook 补锚点。

## AgentFS（Turso）能否减复杂度（本机实测 v0.6.4）

**本机已装**：`/Users/yaoshiping/.cargo/bin/agentfs`，**v0.6.4**。根文件系统 APFS。

**结论：能减，而且精准命中我们最硬的三块（层分离 / 打包规则 / 算 diff）；但它是"执行用的文件系统"，
代价落在测量可信度上，而且它最值钱的那一半切不开。**

**它消掉什么**（对着我们自己的复杂度清单）：
`base/dirty` 两层划分（`agentfs init --base <dir>` 是一等机制）· `EditedFiles` 反向剥离（丢 delta 即可）·
打包规则（没有 tar 了；`mount` 还有 `--uid/--gid` 可归一身份）· 内容寻址（单文件即身份）·
`ChangedPaths` 的 `git add -A -N` hack · `materializeGit`/`materializeFiles` 两分支 + 空仓库陷阱 +
`rev-parse --verify HEAD` 探针（塌缩成一个挂载点）· `git bundle` 兜底（单文件可搬）·
`--workspace-cwd` 对非 git 目录的拒绝。

**实测确认的能力**：`agentfs init demo --base <dir>` → `agentfs fs demo write /a.txt changed` +
`write /c.txt new` → `agentfs diff demo` 输出
```
M f /a.txt
A f /c.txt
```
即**非 git 目录也直接得到改动清单 + M/A 分类**。base 目录内容**未被改动**（`cat base/a.txt` 仍是 `hello`），
COW 成立。`agentfs exec <id> <cmd>`（mount 到临时目录、以它为 cwd、跑完自动卸载）正好对应
`sandbox.ExecStream` + `sb.Root()`，**接缝不用改**。

**实测踩到的三个坑（都值得写进设计）**：
1. **官方首页那句 `cp agent.db snapshot.db` 是错的**：库是 WAL 模式，写入落在 `demo.db-wal`（当时 325KB），
   `.db` 只有 4096B。只复制 `.db` 得到的快照**读不到任何 delta**（`fs cat /c.txt` → File not found），
   **静默**。必须连 `-wal`/`-shm` 一起复制或先 checkpoint。（同一个教训第二次踩：读 git-ai 库时也要一起复制。）
2. **CLI 读路径 ≠ 挂载读路径**：`agentfs fs demo cat /sub/b.txt`（未改动的 base 文件）报 File not found，
   而 `diff` 并不认为它被删。用它当工作区之前必须在**挂载态**验证。
3. **`.agentfs/<id>.db` 就在工作目录里** → 会进 diff / manifest / 快照，collect 必须排除。

**它不解决**：起点时机（仍是必须在**会话开始时**冻结的**计时义务**，不是打包问题）· 非 git 目录的起点
仍是后态 · grader / ground truth。
**它新增**：POSIX 语义保真风险（scandir 顺序 / flock / mmap / xattr / 硬链接 / socket；SWE-bench 已因
"换文件系统顺序变了"产出 `ordering_artifact` 假失败）· macOS 默认走 **NFS**（`--backend` 默认 `nfs`，
Linux 才是 FUSE 生产路径）· **ALPHA**（官方自述）· build/test 全跑它上面的性能成本。

**不可切分（最关键）**：层分离只在 agent **写入经过它**时才成立。执行留 APFS、只借它算 diff ⇒ 拿不到层分离。
所以它跟"要不要上 docker"是同一类问题：核心收益来自"起点在还是真的那一刻被固定"，而 AgentFS 让**捕获**
变便宜又完整（`agentfs init --base <cwd>`，与上一轮的 SessionStart hook 互补，锚点从
"commit + dirty 计数"升级成"确切的那棵树"）。

**零依赖的替代（今天可用）**：APFS clonefile —— 实测 `cp -c -R` 复制 64MB 树 **0.011s**，符号链接保留，
空间按分叉块计费。但它只给"便宜的复制/冻结"，**不给"可查询的层分离"**（仍需 git 或 manifest diff）。
所以决策规则：**痛在"每个 cell 克隆工作区太贵 / 起点会漂移" → clonefile 就够；
痛在"分不清哪块是环境哪块是答案" → 只有 AgentFS 那类机制能救，而它要求执行也搬过去。**
**验证方式**：拿现有数据集跑一次校准实验（APFS vs `agentfs exec --backend nfs` 两次），
数字差异超出噪声就否掉 —— 符合本项目"测量而非假设"的路子。

## 「会话开始建 agentfs mnt，回放用这个未被修改的 mnt」是否成立（实测否，但只差一步）

**实测证据（agentfs v0.6.4）**：
- `fs_overlay_config` 表**只有一行**：`base_path = <那个目录>`。整个"base 层"就是一条路径。
- base 树 8MB，库 `a.db` 只有 4096B（+197KB WAL），`fs_data` **0 行 0 字节**；写一个文件后才有 1 行 5 字节。
  → **base 内容从不落库**，未触碰的文件在**访问时**从磁盘那个目录现读。
- `agentfs fs <id> cat /f.txt`（仅 init 过的 base 文件）→ **File not found**：**CLI 子命令只看 delta，
  base 只有挂载态才看得见**（所以别用 `agentfs fs` 验证 base）。`fs ls` 同理。
- `agentfs init b --base .agentfs/a.db` → **`Error: Base path is not a directory`**：
  **db 不能当 base**，回放不能"以会话那个 mnt 为 base 再开一个"。
- `agentfs exec` 挂载在受限环境里失败：`Error: connection pool timeout: no connections available`
  （macOS 走 NFS）。要在正常终端复核 —— 但 CI/沙箱这类环境里跑不动本身是个问题。

**结论：方向对（起点必须在还真的那一刻固定），但这一版不成立，两个硬伤**：
1. **`--base` 是活路径引用，冻结的是零**：今天谁改一下那个目录（你自己编辑 / 另开会话 / `git checkout`），
   "未被修改的 mnt 的起点"就跟着变 —— 与"`ref` 是分支名会漂移"**同一个病，下沉了一层**。
2. **db 不能当 base** → 冻结的起点**最终必须是真实目录**，原来省不掉的物化一点没省。

**修法只差一步：让 `--base` 指向一份克隆，而不是活目录。**
`cp -c -R <cwd> <store>/<tree-hash>` → `agentfs init <sid> --base <store>/<tree-hash>` →
`agentfs exec <sid> claude ...`。base 是自己的、内容寻址命名的、没人会动它 → 起点钉住；delta = 答案；
回放 `init --base <store>/<tree-hash>` 开新 delta，起点逐字节相同。额外收益：**同一棵树复用同一个 base**
（`dataset_hash` 天然稳定），且**非 git 目录第一次也有起点**。

**必须改一处：不能在 SessionStart hook 里做。** hook 触发时 Claude Code 已用真实 cwd 启动，
**hook 无法把会话的 cwd 搬到挂载点**。要让写入落在挂载上，必须**在 `claude` 启动之前**建立挂载 ——
即**包一层启动脚本 / alias**（`agentfs exec <id> claude`）。上一轮的 hook 设计在这里要改角色：
SessionStart hook 只能"记锚点"，不能"换工作区"。

**两个必须声明的语义**：① 会话前的未提交改动会被 base 收进去（这次是**好事**，那确实是真实起点），
但报告要写清"起点 = 会话前工作树现状，含未提交改动"，否则读者以为是 HEAD；② **环境 ≠ 工作区** ——
env / `~/.claude/skills` / `.gitconfig` / 树外依赖 / 网络 / OS.arch / claude 版本都在这个 mnt 之外
（同 docker 那一轮的清单），只钉住了文件系统那一半。
