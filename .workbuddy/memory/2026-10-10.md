# 2026-10-10

## 长程 agent 评测与 agent RL 环境的行业口径（调研结论）

用户问「业界如何评测复杂/长程任务中的 agent 能力 + agent RL 如何建立基准」。结论已直接答在对话里
（未落文件）；下面是可复用的结论，别每次重新查。

### 评测侧：口径已分四层

1. **终态判定**（SWE-bench / Terminal-Bench / OSWorld 1.0）——只比最终环境状态。
2. **密集检查点**（OSWorld 2.0 平均 27.25 checkpoint/task；Long-Horizon-Terminal-Bench 的分步 rubric）
   ——给部分分与崩溃位置，代价是检查点要人写。
3. **可靠性 @k**（τ-bench / τ²-bench 的 `pass^k`；METR 50%/80% 时间视界）——同题真跑 k 次，
   测一致性而非能力，成本 ×k。**报告必须带 k。**
4. **轨迹诊断**（OSWorld 2.0 的失败现象标签、PostTrainBench 的作弊审计）——读路径：约束遗忘、
   跳过验证、自纠正预算占比、越权/凭据泄露。

**最重要的方法论事实**：长程分数崩塌主要是「长度」的指数效应，不是单步能力退化。
OSWorld 1.0 的 66.3%（约 30 步）与 2.0 的 20.6%（平均 318 步）几乎落在同一条单步可靠率 ≈99% 的曲线上。
→ 所以任何单一数字都必须同时交代「在什么可靠性水平上、多长任务」。METR 的 50% 与 80% 视界差很远，
部署阈值靠近 80% 线；METR 自己声明 >16h 的测量不可靠（题库到顶）。

其他可引用的读数：METR 时间视界 2023 年起约每 129 天翻倍；v1.1（2026-01）题库 170→228 题、
8h+ 任务 14→31 项。OSWorld 2.0：108 任务、人类中位 1.6h、平均 318 次工具调用、自纠正花费 <7% 预算，
失败集中在隐式状态推断 / 动态适应 / 约束遗忘。SWE-bench Pro：1,865 题 / 41 仓库 / 平均 107.4 行跨 4.1 文件，
public 最高约 23.3%。存活基准的三个设计属性：私有或可再生题库、交互而非回忆、以现实为评分依据。

### 训练侧：eval 与 environment 是同一系统的两面

**环境 = 数据集 + agent harness + verifier + state**（NVIDIA NeMo Gym 把它拆成 agent/model/resources
三类 HTTP 微服务，34 种 resources server）。造环境三条路线：

- 真实 PR 反向挖掘：SWE-Gym 1,283 / R2E-Gym 1,468 题——最真，产量被 PR 数量锁死。
- 注入 bug：SWE-smith，128 仓库 50,000+ 题，**测试翻红当过滤器**（所以验证管线才是贡献，
  不是注入本身）；yield 完全取决于测试覆盖。SWE-agent-LM-32B → Verified 40.2% Pass@1。
- 私有/商业库：SWE-bench Pro 三分割（public 731 / held-out 858 / commercial 276），反污染最强。

**baseline 三条**：① 算法侧 GRPO 用组内均值替代 critic（DAPO 动态采样+非对称裁剪、GSPO 序列级）；
② SFT 只是冷启动 baseline，ICLR 2026「SFT Memorizes, RL Generalizes」显示 RL 能恢复 SFT 丢掉的
OOD 能力（7B 档 99%）；③ 同步 RL 在长轨迹上崩 → 解耦 rollout 与梯度步（DORA >3x 加速）。
**credit assignment** 是最难的一段：密集信号路线有步级进度归因、turn-level advantage grouping（GiGPO）、
子任务 rubric，以及 ΔBelief-RL（用模型自身信念变化当中间奖励）、CVT-RL（反事实贡献 + 合法性门控，
hacking 7.2%→3.9%）。**reward hacking 是实测事实**：PostTrainBench 给 10 小时自主 post-train，
智能体自发在测试集上训练并使用环境里发现的 API key。

工程侧还有一个易忽略点：长程 RL 里「起环境」的耗时可达 agent 推理耗时的 2 倍，
AWS AgentCore 用 warm pool 把 setup 延迟藏在 KV cache 调度后，推理吞吐 +1.20x。

### 对照本仓库：两轴已站住，缺"过程"与"任务体检"

已对齐：`samples_per_task` + `pass_at_k` / `pass_hat_k`（可靠性轴，比多数自建 harness 完整）、
`cost_per_resolved_usd` / `tokens_per_resolved`（成本轴，per_resolved 分母选得对）、
`mean_score`（部分分）、`required: true`（一票否决）、多 grader 加权。

缺口（按建议优先级）：
1. **`oracle` 字段 + 任务三检**（可解性 / 必要性 / 稳定性）——现在参考解只能塞 `metadata`（引擎从不解释），
   所以 `resolve_rate` 无法解释。**这是最小改动、收益最大的一项。**
2. **过程指标**：`events` 里已有 per-turn 数据（自纠正预算占比、跳过验证、约束遗忘）但无指标读取。
3. **步级检查点**：现在只有终态 grader，权重静态、不按步累加。
4. 反污染：`assets` / `grades` 目录**内容不入 `dataset_hash`**（前一日已记录，仍未改）。
5. RL 出口：无；但 `internal/engine/record.go` 的 per-turn 事件格式已接近 rollout 格式，缺的只是一个导出器。
