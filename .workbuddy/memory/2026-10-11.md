### 侦察结论（改代码前必读，省一次通读）

- **评测主流程**：`Engine.Run`（`internal/engine/engine.go`）→ `plan()` 展开 task × sample 成 cell →
  每 cell 一个 sandbox → 物化 workspace → setup → agent → 采集 output → grader → `saveCell` → `computeMetrics`。
- **奖励现状**：只有 `Grade.Score`（grader 加权分）+ `Grade.Passed`（= score ≥ threshold 且 required 全过）。
  `TaskResult.Passed()` / `.Score()` 是唯一对外口子。**没有 `reward` 概念，也没有 `oracle`。**
  threshold 来自 `Config.GraderThreshold`（默认 `grader.Threshold`=1.0），task 级可覆盖（存 `grade.Threshold`）。
- **存储表**（`internal/storage/schema.sql`）：`runs` / `task_runs` / `grader_results` / `tool_calls` /
  `run_metrics` / `run_tags`。**没有任务健康检查表**。
- **轨迹已经在库里**：`task_runs.attempt_json` / `trace_json` / `grades_json` + `tool_calls` 表 +
  `raw_stream_path` 指向沙箱外的 `stream.jsonl`。→ **导出 RL 数据不需要新增采集，只需要新出口。**
- **CLI 子命令**：`run / validate / list|ls / report / compare / serve / registry|metrics / version / help`。
- **Web 路由**（`internal/web/server.go`）：只有只读 `GET /api/runs`、`/api/runs/{id}`、
  `/api/runs/{id}/tasks/{task}`，加一个受三重守卫的 `POST /api/runs/{id}/delete`。**没有环境/rollout 端点。**
- **dataset spec**（`internal/dataset/spec.go`）：`TaskSpec` 有 Prompt/Workspace/Output/Graders/Limits/Metadata；
  `Metadata` 明确「引擎从不解释」——参考解目前只能塞这里，等于死数据。

### 提出的三层契约（按依赖顺序，RL 对评测端的要求）

1. **奖励必须可信**——`reward` 契约（显式声明 pass / score / expr，而非隐含在 threshold 里）+
   `oracle` 字段 + `aeval audit` 三检（可解性 / 必要性 / 稳定性）+
   `restore_paths` / `forbid_changed_paths`（RL 下这不是防作弊，是让「改测试拿分」不成为最优策略）。
   动：spec.go、engine、新子命令 audit、schema.sql 加健康表、report 显示。
2. **轨迹必须能出去**——`aeval export --run <id> --format jsonl`，一条 = 一次 rollout
   （task_id / split / prompt / turn 级轨迹 / reward / grader 明细 / dataset_hash / config_hash / model / seed），
   支持 `--split train|eval`、`--healthy-only`、`--min-reward`。**纯新增，不动现有语义。**
   诚实边界：Claude Code CLI 不吐 token id / logprobs → 只能 turn 级，**不能喂 PPO 的 token 级 importance sampling**，要写进文档。
3. **环境可服务化**——`serve` 加 RL 端点（任务目录 / 跑一次 rollout 返回 reward / reset）。
   最大也最危险：威胁模型从「渲染模型输出」变成「远程执行 + 花钱」，必须 loopback 默认 + 显式开关 + 并发与成本上限。

## 换模型重跑 baseline 数据集（同日，第三轮）

### 用法
- 单次对照：`aeval run --dataset <ds> --bin claude --model <new> --name <n>`。
  `--model` 原样透传给 CLI；空值则用 CLI 自己的 `ANTHROPIC_MODEL`。
- **正道**：`aeval matrix` 的 model 轴 sweep（新增 `examples/matrix-model.yaml`），
  control 与 level 跑在同一 harness 下，再逐任务配对。

### 三条实测出来的问题

1. **数据集是「时间胶囊」，代码改进不会回溯修复旧产物**（不是解析 bug）。
   `datasets/local_claude_code` 是 cost-state 解析接上**之前**采集的：
   `baseline_ms` 没写、tokens 254,510（真值 **528,296**）、cost 0。
   同一份转录重采后 `busy_ms=20818 / duration_ms=752430 / cost=$0.570`。
   → 对比前先确认 baseline 字段不是空的；数据集要随采集器一起重采。
2. **采集器不写 `workspace`**：`cwd` 只落在 `metadata`，采出的是
   `{"type":"empty"}` → agent 在空目录里被要求「找 queryLoop 主循环」。
   用 `--workspace-repo/--ref` 绑。**附带坑**：一旦绑 repo，采集器把
   `output.type` 推成 `patch`，而行只读问答任务交付的是文本 →
   要 `--output-type stdout` 显式覆盖。
3. **【已修】baseline 缺测量时仍给出差值**（见下）。

### 已修：`Ms == 0` / `Tokens == 0` 是「没记录」，不是 0
实证：旧数据集跑出 `vs baseline -228.0k tokens, +23.4s` —— 那个 `+23.4s` 是拿
本次 23.4s 减 baseline **从未被测量**的 0。`compareToBaseline` 里
`if busy == 0 { busy = b.DurationMs }` 救不了，因为两个字段都是 0。

修法（规则仍只收在 store 一处）：
- `store.Attempt.TokenDelta()/MsDelta()` → `(value, ok)`，`ok=false` 当
  `b.Tokens<=0` / `b.Ms<=0`。与 `ComparableBaseline` 分工：
  那个答「有没有基线」，这个答「基线里有没有这个测量」。
- `runner.Summary` 加 `TokenCells` / `TimedCells`。**求和之后「差值为 0」与
  「没测量」再也分不开**，所以必须带计数 —— 这条理由写进了注释。
- `report.metrics` 按各自计数门控（不再只看 `BaselineCells`）；`BaselineView`
  加 `HasTokens/HasTime`；`app.js` 的 `baselineCell`/`baselineRows` 缺测量时
  显示破折号或「no … to compare against」；CLI 摘要分段打印。
  旧数据集现在 `-254.5k tokens across 1 cell(s)`，新数据集
  `-528.3k tokens, -19.2s`。

### 实测数字与一个更根本的陷阱
- 同一份转录 **wall 752,430ms vs busy 20,818ms（36 倍）** —— 墙钟不可比，
  比之前那个 8.3x 的例子更极端。
- **录制会话不能当模型对比的 control**：它的 harness（用户的 CLAUDE.md、
  skills、hooks、12 分钟 9 轮）与 clean room 完全不同，
  `vs baseline -511,511 tokens` 里混着模型 + harness + 会话形态三件事，
  对哪一件都不能下结论。这正是 model 轴 sweep 存在的理由。
- 实测 `examples/matrix-model.yaml`（1 个任务 → 1 对配对）：
  flash 28.9k/21.0s/7 轮/10 次工具调用 vs pro 6.6k/15.0s/3 轮/2 次，
  **p=1.000**（1 对配对，符号检验到不了显著，工具如实报 no_clear_difference）。

`#161a21`（=`--panel`），且从 y=0 到底、左边界恰好 440 = 1440−1000。
`.drawer` 是 `position:fixed; right:0; width:min(1000px,78vw); background:var(--panel)`。
在页面里注入探针列出所有 fixed/absolute 元素 → `<aside class="drawer" hidden>`，
**0 个子节点**，占位 1000×913。即：不是布局被挤窄，而是**空抽屉盖在上面**。

根因：`hidden` 属性在 UA 样式表里是 `display:none`，**任何作者规则设了 display 都会赢**，
而 `.drawer { display: flex }` 正好设了。`hidden` 因此形同不存在。

修法：`app.css` 加 `.drawer[hidden] { display: none; }`（并删掉同处空规则
`.drawer.cmp, .drawer-left, .drawer-right { }`）。JS 侧不用改：`drawer.hidden=false`
去掉属性后 `.drawer` 的 flex 照常生效（实测 点击行 → display=flex, kids=2, w=1000）。

护栏：`report_test.go` 新增 `TestHiddenElementsCanActuallyBeHidden` ——
从 shell 里扫出所有带 `hidden` 的元素类名，若样式表给该类设了 display，
就必须存在对应的 `.cls[hidden]` 规则。**做了变异验证**（把规则改名 → 测试失败 → 改回），
不是空转断言。附带 `cssRules()` 浅解析（必须先剥注释，否则规则前的散文会被当成选择器）。

工具备注：本机 headless Chrome 的 `--screenshot` 是可信的（与 DOM 探针一致），
但 `--dump-dom` 的输出里**先出现的是注入脚本自身的字面量**，grep 要取最后一个匹配。

## 问答：`aeval run` 会加载已有的 skills 吗

**不会**。默认命令行长这样（用 `agent.BuildCommand` 打印，临时测试跑完即删）：

```
claude -p --output-format stream-json --verbose --session-id <uuid>
       --model <m> --permission-mode bypassPermissions
       --bare --strict-mcp-config --disable-slash-commands
```

关键认知（容易被 `--bare` 误导）：**挡住 skill 的不是 `--bare`，是
`--disable-slash-commands`**。本机 claude 2.1.296 的 `--help` 明写
`--bare` 那句是「Skills still resolve via /skill-name」，而
`--disable-slash-commands` 的说明就四个字「Disable all skills」。

要真的加载（skill 轴）：`--plugin-dir <dir>` + 把 `disable_slash_commands` 关掉。

保留 `disable_slash_commands: true` 则被 `checkSkillLevel` 拒绝。
注意 **`isolation` 属 harness 轴**，所以只能在**共享配置**里关，
不能按 level 关（那是跨轴改动，加载期拒绝）。

### 用户问「c3bcb5a5 为什么还是少了这么多 token」→ 查出 run 侧记账错

**真 bug**：`Attempt.Usage()` 读 `Trace.Result.Usage` = **一次 API 调用**的用量，
而会话累计在 `result.modelUsage`。单 result 事件时两者有时恰好相等（所以潜伏很久），
本次该 run **派了后台搜索子代理 → 流出两个 result 事件**，parser 让后一个覆盖了前一个，
读到的正是最小的那份：报告 **18,540** vs 真值 **164,419（少 89%）**。

修了 4 处 + 1 处顺带发现：
1. `trace.Trace.Usage()`：优先 `modelUsage` 求和（空则回落 `usage`）；`Attempt.Usage()` 走它。
2. `applyResult`：多个 result 事件是**同一会话的累计快照**→ 按总量最大的一份合并（幂等）；
   `total_cost_usd` 同理。描述「答案」的字段仍取最后一个事件。
3. `Trace.Turns()`：优先流推导的 `TurnCount`（`result.num_turns` 在多 result 事件时是 1）。
4. `runner.applyUsage` 改用 `Turns()`。
5. **`collect.metadata` 顺带发现的自相矛盾**：`baseline_tokens`/`baseline_ms` 读会话总量，
   `--split turn` 下与自己的 baseline 文件不符（528,296 vs 108,935）。改为取切片值。

护栏全部变异验证过；新 fixture `internal/trace/testdata/multi_result_stream.jsonl`
是那条真实流（50 行，2 result 事件 / 11 轮），测试断言它仍能区分「一次调用」与
「一段会话」，避免变成空转。`go test ./...` 13 包全过。

**用户看到的差距另有一半是真实的**：baseline 是**整段会话**（含第二个无关提问
「当前的sessionid是什么」），528k 里 **471,296 是 cache read**（89%），且模型是
**deepseek-v4-flash**。按新鲜 token(in+out) 比：baseline 57,000 vs run 77,635
