## 设计讨论：多轮对话该怎么「回放」（结论，未改代码）

起因是一个问题「多轮对话，应该如何回放」。**结论：回放的单位不是「轮次」，是「自包含的任务」；
一段多轮会话里只有第 1 轮真正可回放。**

**代码事实**（先把缝隙定位准）：`collect` 把整段存下来了（`Session.Prompts` 全部人工轮 +
`Session.Turns` 含 user/assistant 角色 → `Baseline.Turns`），但**回放路径只吃一句**：
`runner.runCell` 把 `t.ResolvedPrompt` 单串写进 stdin，`agent.ClaudeCode.Run` 一次 `ExecStream`，
session id 只用于事后关联。`SplitSession` 取 `Prompts[0]`，`SplitTurn` 每轮一个格子 —— 两者都
**不会把第 2 轮再喂回去**。所以现状是「多轮录制 + 单轮回放」，不是多轮回放。
`--resume` 是 cell 级续跑，与会话续接无关。

**三种语义与结论**：

| | 做什么 | 判定 |
| --- | --- | --- |
| A 单发 | 只喂第 1 句，agent 自行跑完 | ✅ 可回放；代价是会话里人工纠偏的轮次变成不可解任务 |
| B 逐句剧本 | 同一会话续灌 U1→U2→U3 | ❌ **不可回放**：后续轮次的指代对象是录制里的那个回答，换了 agent 就成了非承接语，测的是幻觉 |
| C 逐轮切片 | 每轮独立格子 | ✅ 诚实但窄：「再改一下那个」这类引用无处落地 |

**核心论证（B 为什么是陷阱）**：后续用户轮次不是独立输入，是**对已发生回答的回应**。「顺便把
刚才那个也改了」里的「刚才那个」指向 A1；新 agent 的 A1′ 不同时，这句话没有指代对象。这与
`spec.go` 里已写下的原则同源：baseline 是「发生了什么」的记录，**不是再跑一遍的脚本**。

**顺带发现一个已存在的隐蔽错位**：`compareToBaseline` 只数 baseline 的 **assistant** 轮
（`runner.go` 里 `turn.Role == "assistant"`），报告里 attempt 的 `Turns` 也是 assistant 轮。
但 baseline 那些 assistant 轮里一大半是在回答第 2、3 个人工轮 —— 所以「本轮 9 轮 vs 录制 14 轮」
这种对比，两边数的不是同一件事。多轮会话的 turns 对比**现在就是不成立的**。

**若要真做，三条路（按性价比）**：
1. **A + 把人工介入次数当指标**（推荐，改动最小）：`compareToBaseline` 从 `b.Turns` 里数
   `role == "user"` 存进 `BaselineComparison`，报告 baseline 卡加一行「人工介入 N 次 / 回放 0 次」。
   这个差值**就是自主性缺口**，现在完全不可见。`TaskSpec` 不用动。
2. **B(仅自包含轮)**：需要 `TaskSpec` 能表达「这一轮的上下文来自哪一轮」（现在 `Prompt` 是单串），
   加一个「本轮是否自包含」的人工标记。`SplitTurn` 的加强版。
3. **C(用户模拟器)**：不是回放 —— 不重放 U2 而是**生成** U2′（据新 agent 的状态），需要
   `agent.Runner` 之上的一层对话循环（claude CLI 有 `--resume <session-id>`）；轨迹从第 1 轮就
   分叉，**录制 baseline 不可复用**。τ-bench 那类交互式基准走的是这条路，但它与新组件同名是误导。

**caveat**：单发回放对 baseline 的 **token** 对比仍成立（都是「跑完这件事」的总量），但对
**turns/轮数**的对比不成立。`SplitTurn` 已经踩过同款坑并记录了（per-turn baseline 的 cost 留空，
因为 cost 不可归给单轮）—— 多轮回放是同一问题的另一个面。

## 业界怎么做多轮（调研结论）

追问「业界的 agent 评测也只回放第一轮吗」。**先要把两个「轮」分开**：

- **人类轮次**：主流确实只给 1 次 —— SWE-bench / GAIA / OSWorld / WebArena / Terminal-Bench /
  METR HCAST。Sierra 自己就批评过这批基准「只评估单轮人机交互，信息一次性给全」。
- **agent 步数**：全都是几十到几百步。**SWE-bench 的 "agentic multi-turn mode" 里的 multi-turn
  指的是 agent loop（EvalScope 实现默认 cap 250 步），不是用户轮** —— 这个命名误导性很强，
  是「只回放一轮」这句话最容易读错的地方。

**真·多轮基准分两类**，分界线是**用户话术从哪来**，这直接决定能不能逐字重放：

| 类别 | 例 | 话术来源 | 逐字重放 |
| --- | --- | --- | --- |
| 合成剧本 | BFCL v3/v4 multi-turn（base/miss_func/miss_param/long_context） | 写死的夹具 | ✅ 可行 |
| 用户模拟器 | τ-bench / τ² / τ³（Sierra）、SWE-Together、AgencyBench、Ambiguous SWE-bench | LLM 现场生成 | ❌ 必须生成 |

BFCL 能逐字喂**不是因为它是真话术，而是因为它是合成夹具** —— 对话是为驱动某条 ground-truth
工具链而构造的，官方明确「static, deterministic offline, no user simulation」。

**没有任何主流基准「逐字重放真实用户的历史话术」。** SWE-Together 把理由写得和上面那段论证几乎
一字不差：「不能把人类历史聊天记录逐字重放给新 agent —— 新 agent 走不同技术路线时，原用户后续的
话就不再 make sense」。它的解法是 **anchored / state-conditional user simulator**：监控 agent
实时轨迹，按触发条件决定「沉默」还是「介入」（question / redirect / new-requirement /
check-external），并由 original user intent 锚定防止跑偏。（109 任务，从 11,260 条真实会话里
筛出，通过率 0.97%。）

**指标随之改变** —— 正好印证上面建议的 A 方案：

- 单轮：pass@1 / resolved rate。
- 多轮：**pass^k**（k 次全成功，测可靠性；τ-bench 里 GPT-4o retail 单跑 60 多分、pass^8 < 25%）；
  SWE-Together 的 **User Correction = #corrections + 0.2·nudge**，且与能力**强负相关**
  （Pearson r = −0.92：越强的 agent 要人纠得越少）；Intent Coverage。

**判分地点一致**：τ-bench / Terminal-Bench / AgencyBench 都明确「判最终环境状态，不判对话文本」
（Terminal-Bench 原文：does not read what the agent said — it inspects what the agent did）。
与本项目「报告是数据库的函数」「grader 读 workspace」同向。τ-bench 另一条可借鉴：**评级用
最终 DB 状态对比标注目标态**，而不是评回复。

**对本项目的推论**：baseline 是**真实录制会话** → 落在「用户模拟器」一类 → BFCL 那套逐字喂
**不能照搬**（前提条件不成立）；要做到 SWE-Together 那样，缺的是一个**锚定在原用户意图上的用户
模拟器** —— 新组件，不是接线。另：`compareToBaseline` 现在数的是 assistant 轮，若照搬业界，
该报的是 baseline 的 **user 轮数**（= 录制里的人工介入次数）。

## ⚠️ 会话中途发现：`SplitSession` 的语义被**并行改写**了

工作区里有另一个写者在同一批文件上改（10:54–11:05 之间 `collect.go`/`parse.go`/两个 test 反复变），
期间 `go test ./...` 一度全红、随后又全绿。**不是我的改动**，但也别当没发生。改了的是：

- `Collect` 拆分出 `turnSlice(s, from)` + `buildItem(s, promptIndex, opts, used)`：
  **`SplitSession` 不再是「整段会话」**，而是「第一个 prompt + 回答它的那些轮」——即 `turnSlice(s, 0)`。
  只有**切片 == 整段会话**（单 prompt 会话）时才用会话级数字（`s.Usage/BusyMs/DurationMs/CostUSD`），
  否则用 `sliceBusyMs`/`sliceSpanMs` 求和并附上「per-turn baseline inside a longer session」注记。
  理由写在代码注释里：多 prompt 会话的整段轨迹是在回答一个任务根本没问的问题，拿它比会让每次回放都
  显得更便宜。**这正是此前设计讨论的 A 方案落地。**
- `parse.go` 同步大改：`TurnDurations` 数组没了，改成 `closeTurn(ms)` 把时钟挂到**最后一个 assistant
  条目**上（排队中的 prompt 会让按序号对齐错位）；cost-state 记录改称**检查点**，其后到达的消息计入
  `uncoveredUsage`，`staleTotals` 记录「检查点之后还有消息」（真实会话里最后一个检查点在第 178/905 行，
  把 token 少报了 14 倍）。

推论：**e2e 里不要依赖「会话总量 = 基线」**，除非会话只有一个 prompt。我的夹具因此把主会话改成单 prompt
（拿到会话级数字），另一个双 prompt 会话专测切片 + 注记。

## 问答：agent 和模型同时变，还能出报告吗（读码核实，未改代码）

**结论：报告能出，归因出不来 —— 而且它不会告诉你出不来。**

闸门只有一处在装：

| 入口 | 闸门 | 证据 |
|---|---|---|
| `matrix`（唯一 sweep 入口） | **有，加载期** | `plan.go:410-423` 逐 level 查 `Changed ⊄ Axis.Owned()` → 报错；`Load` 在 `plan.go:325` 调 `validate()`，`runSweep` 在 `main.go:1080` —— **一个 cell 都不会跑** |
| `run` | **没有** | 没有 plan 就没有「轴」；Spec 里同时给 `kind`/`bin` + `model` 完全合法 |
| `report --compare a b` | **没有** | `LoadComparison` 只投影；`Compare` 结构体（`model.go:331`）**连 Warnings 字段都没有**，不比 AgentKind/AgentModel，**也不比 DatasetHash**（`DatasetDrift` 只用在 sweep 路径 `load.go:73`） |

`kind`/`bin` 归 **harness** 轴：`Axis.Owned()` 的 default 分支收集「不在 `modelOwned`/`skillOwned` 里的 specKeys」，`kind`/`bin` 都落这里（`plan.go:86-106`）。所以「换 agent + 换模型」= harness + model = **两条轴**。

**为什么救不回来**：delta = Δagent + Δmodel + 交互，一个方程三个未知数。是**识别问题**不是功效问题（加 samples 没用）。`plan.go:20-28` 的包注释本来就写明 OFAT 看不见交互。

**唯一合法形状**：2×2 析因 = **两次单轴 sweep**（`axis: harness`，分别 `--base M0` / `--base M1`），因为 `--base` 改的是所有 level 的公共起点、不动 `Level.Changed`，每次仍只动一轴。然后 交互 = [(M1,A1)−(M1,A0)] − [(M0,A1)−(M0,A0)]。

**顺带核实的新缺口**（和 Cursor 那条线直接相关）：录制方身份**在落库时丢了** —— `dataset.Baseline` 有 `AgentName`/`AgentModel`/`Source`/`Notes`（`spec.go:198-228`），但 `store.BaselineComparison`（`store.go:207-222`）一个都没有。所以 Cursor 录的基线（`agent_name: cursor`）被 claude-code 回放时，报告那行「录制 vs 本次」**看不出是跨 agent 比较**。这和上面是同一种病：**比较器不检查两边是什么**。最小修法是给 `LoadComparison` 加一条不一致警告（照 `att.DatasetDrift` 的写法）；完整修法是 v3 把 `Baseline.AgentName/Source/Notes` 带进 store。

1. `buildItem` 的 baseline 注记：`SplitSession && len(s.Prompts)>1` → 「the recorded session holds N

   任务仍在数据集里，只数追加的会在每次重跑时误报「部分收集」）。建议随 split 变：session → 换
   `--split turn`；turn → 调低 `--min-prompt-runes`。dry-run 路径也打。
3. 顺手修 `SplitSession` 的文档注释：原写「measured against the whole recorded trajectory」，
   对多 prompt 会话不成立（实际是切片的）。

**实测三条路径**：默认 → `warning: 1 session(s) hold more prompts … 1f2114cd (1 of 3)`；`--split turn`
→ 无此警告；追加路径（`skipped 1 already collected`）→ 警告照常且不误报。

## `--chain-sessions`：把同一会话的轮次串成一条链（用户提的需求）

**用户问**：「加上 split turn 之后，run 的时候可否按照 split 的顺序 run，同时同一个 session 的运行
目录保持一样」。答案：加了 `--chain-sessions`。

**为什么这不是「顺手加个 flag」**：`--split turn` 默认把每条 prompt 规划成独立 cell（各自空沙箱、按
`--concurrency` 恰好排到的顺序跑）。对「人在一直追问」的录制这是错的——第二条 prompt 问的是第一条
写下的那个文件，在新目录里回放等于在问一个从没存在过的文件。而**顺序**和**同一目录**是同一件事的
两面：目录一样，第二个 cell 才能看见第一个留下的东西；顺序不对，看见的就是错的东西。

**改动落点（八层，缺一层就有一处沉默）**：

1. **`dataset.TaskSpec` 加 `Session string` + `PromptIndex *int`**。不是塞进 `metadata`：`metadata`
   契约上「引擎从不解释」，而这两个值引擎**必须读**（分组 + 排序）。`collect` 两个 split 都写。
2. **`session/collect.go`**：`task` 里带上这两个字段（`intPtr` 小工具）。
3. **store v5 = `runs.chain_sessions`**。理由：attempt 行上**没有任何一列**能事后推出「这些 cell 是
   一条续写而不是独立采样」。`addColumnIfMissing` 幂等，v1/v2/v3 夹具各补一句 drop。
4. **`runner.plan`**：先按 `{chain, sample}` 分组（`chainKey`：开链式且有 session → `pathName(session)`，
   否则 `pathName(task.ID)`），**保留首次出现的组序**，组内 `sortChain`，再标 `first`/`last`。
   目录 = `root/<runID>/<chain>/s<sample>`。
5. **`sortChain` 只在每个 cell 都有 `PromptIndex` 时排序**，否则退回数据集顺序（半个键不是键）。
6. **物化/清理各一次**（`runCell`）：只有 `first` 物化、只有 `last` 删。**物化失败污染整条链**：
   `execute` 维护 `broken[chain]`，之后每个 cell 记 `fail(...)` 而不跑（否则会写出「agent 答得不好」
   的行，而真相是工作区没建起来）。
7. **`Config.Validate()` 是单独一个纯方法**：链式 + `--concurrency > 1` → 报错。CLI 调它才能把 flag
   错误报成 **usage error（exit 2，实测）**，而不是「开跑之后失败」。`--resume` 用 `chainsIntact`
   拒绝半条链（点名链名与 `2 of its 3`）。
8. **`pathName` 是安全边界**：session id 实践上是 UUID，但任务文件是给人手改的，带分隔符的名字会把
   工作区放到 run 目录之外。白名单 `[A-Za-z0-9._-]` + trim `-.` + 空则 `task`。

**披露三件**：run 行 → 报告头部 chip（`k=` 旁边，`raw()`）→ `comparisonWarnings`（「链式的与普通的
不是同一种测量」）。链式决策也打一行 stdout 提示：`chained: each session's tasks share one workspace
and run in order, so the cells of a chain are a sequence rather than independent samples`。

**真实二进制复核**（`/tmp/aeval4` + `tests/testdata/agents/chain.sh`）：
- 不链式 → `passed 1 (50.0%)`（第二个任务答 `missing`）；链式 → `passed 2 (100.0%)`。
- `--chain-sessions --keep` 落盘只有一个目录：`workspaces/<runID>/s1/s0/`，里面躺着 `handoff.txt`
  —— 第一个 cell 写下、第二个 cell 读到的那个文件。
- `--chain-sessions --concurrency 4` → **exit 2**，`chaining a session's tasks gives them one workspace
  and runs them in order, so it cannot keep 4 cells in flight at once`。
- 报告载荷：链式 `"chain_sessions":true`；不链式整份 HTML 里只有 app.js 源码里那一处字面量（omitempty）。

**变异验证 14 项，全部确认变红**（脚本化，每项只破坏一个决定、跑声称钉住它的那条测试、再还原）：
丢 `sortChain` / `chainKey` 忽略 session / `pathName` 用原始 id / `Validate` 恒 nil / `first` 恒 false /
`last` 恒 true / `chainsIntact` 永不拒绝 / 删 baseline 注记 / 删 `warnDroppedPrompts` 调用处 /
`boolInt(r.ChainSessions)` 写死 false / `scanRun` 读回恒 false / `load.go` 字段写死 false /
`comparisonWarnings` 链式分支删掉 / **app.js 的 chip 条件改 `false`**。

**最后那条为什么要跑浏览器**：chip 是 JS 运行时画的，**在 HTML 里 grep 到那个字符串只证明源码被装
进去了**——这正是 `[object HTMLDivElement]` 当年潜伏的方式（文件、载荷、退出码全对，套件全绿）。
所以给 `tests/render_test.go` 的探针加了「读回 `.card.runhead` 的 textContent」，新增
`TestReportHeaderSaysTheCellsWereChained`：跑一份链式数据集 → 浏览器渲染 → 断言头部含

## 顺手撞见并修掉的既有 bug：`report --compare a b --db X` 必然找不到 run

给链式做真实二进制复核时想演示「链式 run 与普通 run 不是同一种测量」，敲了最自然的写法：

```sh
aeval report --compare plain chained --db cmp/a.db -o cmp/c.html
```

→ `aeval: report: store: run plain not found in aeval.db`。**注意它说 `aeval.db`，而我传的是
`cmp/a.db`** —— 这个「点名的文件不是我传的那个」正是设计约定 #13 当初加 `NotFoundError{Path}` 要暴露
的那类线索。`list --db cmp/a.db` 明明能列出这两个 run（`aeval report --run <id> --db cmp/a.db` 也正常）。

**根因**：`cmdReport` 先 `openStore(&common)`（默认 `aeval.db`），**之后**才在 `--compare` 分支里调
`positionals()` 去回收写在位置参数之后的 flag。Go 的 `flag` 遇第一个非 flag 就停，所以
`--compare a b --db X` 里的 `--db X` 在第一次解析时根本没被看到；等 `positionals()` 把它捡回来，
**store 早就开在默认路径上了**。

**为什么一直没被发现**：`--db` 写在 `--compare` 前面的形状一直是好的，而**本文件里两处既有 e2e
（`TestCLIRunsTheDemoDataset`、`TestCLIProvesWhichSkillsARunLoaded`）恰好都是那个形状**。也就是说，
工具邀请的写法正是唯一没被任何测试走过的写法。

**修法**（一行位置）：把 `trailing, code := positionals(fs, stderr)` 提到 `openStore` **之前**调一次，
`--compare` / `--run` 两个分支复用结果（不再各自调）。`positionals` 现在全文件只有一处调用点。

**护栏** `TestCLIComparesTwoRunsHoweverTheFlagsAreOrdered`（用 `chain.sh` 那份无需 pytest 的数据集，
两个 run 一次落进同一个库）：两种 flag 顺序渲染出的载荷**必须逐字段相同**；再拿一个空库比一次，
断言错误点名的是**调用者传的那个路径**、且**不出现 `aeval.db`**。

**变异验证**：把 `openStore` 挪回 `positionals` 之前 → 测试红，红的信息就是原来那句
`run aa7d0a8e-… not found in aeval.db`（而 `--db` 传的是临时目录里的库）。至此本轮累计 **15 项变异**
全部确认变红。修复后 `gofmt -l` 干净、`go vet` 过、全量 13 包再绿（`tests` 80.9s）。

**顺带查清、不打算改的一件事**：`--run` 和 `--compare` 都**只认 run id，不认 run 名**（`report --run
plain` 同样报 not found）。这是**一致的**，不是缺口：`runs.name` 在 schema 里**没有唯一约束**，按名字
查会是有歧义的；而 `run` 的 `Next:` 提示与 `list` 的第一列给的都是 id，工具本来就一直把 id 递到手里。
所以不改（要改就是给 name 加唯一约束 + 一套歧义处理，是另一个决定）。
